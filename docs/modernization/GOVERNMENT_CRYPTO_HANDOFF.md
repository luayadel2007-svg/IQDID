# Government cryptographic handoff

Status: DEMO ONLY. No official verification, production keys, sovereign PKI, authentication or persistence is implemented. G1a/G1b remain unpassed. See [CRYPTO_READY_INTERFACE_MAP.md](CRYPTO_READY_INTERFACE_MAP.md) for exact signatures and [NO_REBUILD_MIGRATION_PLAN.md](NO_REBUILD_MIGRATION_PLAN.md) for data work.

## Files and engineering work to implement

1. Keep existing pages and gateways for Demo. Build C3/C4/C5/C2-B as separate services; add a reviewed real transport mapping from service DTOs into a versioned domain/view model. Do not decode a protocol response as DemoVerificationSession. Real result rendering will require a bounded UI integration change and new tests.
2. Implement `KeyProvider` and `SigningPort` behind server adapters. Use non-exportable KMS/HSM handles, least-privilege service identities, per-purpose keys, explicit algorithm allow-list, versioned key references and audited signing policy. Never expose signing handles/material to UI DTOs or public tables. WebCrypto/device keystores may suit holder-device operations after capability review; server sovereign keys belong in managed infrastructure.
3. Keep the protocol SDK entry in `packages/api-client/src/server/compatibility/`. Wire the existing TASK-3C adapter around every relevant SDK boundary. Retain F01–F06 guards and historical SDK_RAW failures. Re-run full SDK and interoperability suites; the four new injected tests are not a replacement.
4. Implement issuance and verification against project-pinned OpenID4VCI 1.0 Final, OpenID4VP 1.0, SD-JWT VC draft -19 and Token Status List draft -21. No silent standard or SDK upgrade, no deprecated @sd-jwt/crypto-nodejs. Resolve policy/contract decisions before using proposal fields.
5. Only mint a server-owned protocol proof after signature/chain/trust, purpose/algorithm, issuer, audience, nonce/replay, holder binding, time validity and authenticated fresh status checks. Reject unavailable/unknown/stale dependencies. Validate public JWKs to exclude private parameters. Protocol result needs distinct rejection/error results in the future versioned real API; current Demo codes must not represent these.
6. Implement trust and status resolvers with configured trust anchors, validity windows, key purpose and version anti-rollback. TrustEntry currently lacks keys; resolve the proposed keys mapping explicitly. C5 must distinguish committed revocation from publication success; never undo revoked state when publication fails. OD-09/CAS and publication responses need an owner-approved contract change.
7. Implement AuthorizationPort independently of crypto verification. Resolve OD-02, OD-06 and related human approval requirements; fail closed if policy is absent. Consent is not an administrator approval or authentication mechanism.
8. Implement SensitiveStoragePort using approved authenticated encryption and key wrapping, AAD bound to record/schema context, envelope versioning, managed access, retention and rotation. Do not log payloads. Preserve relational identifiers where lawful, but assess search/index leakage separately.
9. Add TLS/mTLS service identities, trust-store provisioning, key issuance/revocation, backup/restore procedures, monitoring, incident response and legal approval. Browser private-key export is forbidden. Transport security does not replace encryption at rest.

## Rotation and acceptance

Introduce a new key version; sign/write with it while reading prior authorized versions during an explicit overlap. Publish verified trust material before usage, track list versions and cache freshness, re-encrypt stored envelopes in bounded batches with reconciliation. Retire old access only after verification of migration and backups. A compromised-key incident may require credential reissuance, not merely database re-encryption.

Required before real activation: existing modernization suite; TASK-3C full adapter and raw SDK evidence; negative signature/trust/nonce/holder/status cases; no SDK bypass; key-purpose separation and no downgrade; HSM failure without fallback; authorization/approval denial; schema migration/concurrent writes; revocation terminality/publication failure; backup restore with keys and rollback tests; external protocol interoperability and independent review. Owners must set evidence retention and pass criteria. Do not label VERIFIED_BY_PROTOCOL on a consent response.
